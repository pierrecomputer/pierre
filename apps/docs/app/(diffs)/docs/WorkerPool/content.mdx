## Worker Pool

<Notice variant="warning" icon={<IconCiWarningFill />}>
  This feature is experimental and undergoing active development. There may be
  bugs and the API is subject to change.
</Notice>

<Notice icon={<IconBulbFill />}>
  Import worker utilities from `@pierre/diffs/worker`.
</Notice>

By default, syntax highlighting runs on the main thread using Shiki JS. Worker
pools move highlighting off the main thread, which can help when using Shiki for
large files or many diffs. The main thread renders plain text first, then
applies highlighted output when a worker responds.

<Notice icon={<IconBulbFill />}>
  [Highlights](#highlights) usually performs best on the main thread. In our
  benchmarks, a pool made highlighted output appear 1.5–4× later and increased
  main-thread work, though it painted plain text sooner. Measure your own
  content before adding a pool. If you pair Highlights with a pool, we recommend
  you set [`mainThreadMaxCharacters`](#worker-pool-main-thread-highlighting) so
  smaller files skip the workers.
</Notice>

Basic usage differs a bit depending on if you're using React or Vanilla JS APIs,
so continue reading for more details.

### Setup

One unfortunate side effect of using Web Workers is that different bundlers and
environments require slightly different approaches to create a Web Worker.
You'll need to create a function that spawns a worker that's appropriate for
your environment and bundler and then pass that function to our provided APIs.

Lets begin with the `workerFactory` function. We've provided some examples for
common use cases below.

Use `@pierre/diffs/worker/worker.js` when your bundler builds the worker and its
dependencies. For static hosting, copy `dist/worker/worker-portable.js` from the
package. The portable build bundles all highlighter backends and their
dependencies into one script, so `new Worker(url)` and blob URLs work without
additional files or a bundling step. It also supports `{ type: 'module' }`. The
pool resolves themes, Shiki grammars, and registered Highlights lexers on the
main thread and sends them to the worker, so the theme and grammar catalogs are
excluded from the portable script.

### Usage

With your `workerFactory` function created, you can integrate it with our
provided APIs. In React, you'll want to pass this `workerFactory` to a
`<WorkerPoolContextProvider>` so all components can inherit the pool
automatically. If you're using the Vanilla JS APIs, we provide a
`getOrCreateWorkerPoolSingleton` helper that ensures a single pool instance that
you can then manually pass to all your File/FileDiff instances.

<Notice icon={<IconInfoFill />} variant="warning">
  When using the worker pool, the `theme`, `lineDiffType`, `preferredDiffLib`,
  `tokenizeMaxLineLength`, and `useTokenTransformer` render options are
  controlled by `WorkerPoolManager`, not individual components. Passing these
  options into component instances will be ignored. A component's
  `parseDiffOptions.preferredDiffLib` still selects the library for its file
  diffs.
</Notice>

Lines longer than `tokenizeMaxLineLength` characters skip syntax highlighting
and show only their start, with a button to show the rest.

To change render options after `WorkerPoolManager` instantiates, call
`setRenderOptions()`. Changing render options will force mounted components to
re-render and clear the render cache.

If you need token callbacks or experimental token selectors such as `data-char`,
enable `useTokenTransformer: true` on the worker pool itself. Worker pools can
move highlighting work off the main thread, but they do not reduce the extra DOM
size created by token metadata. For token callback behavior and performance
tradeoffs, see [Token Hooks](#token-hooks).

Set `useTokenTransformer: true` on the pool when pool-rendered files can enter
[edit mode](#edit-mode). A file being edited renders on the main thread with the
token metadata the editor reads, while the pool keeps rendering every other
file. Pool markup rendered without the transformer lacks that metadata, so
entering edit mode re-highlights and re-renders the whole file synchronously
before anything paints, which blocks the page for seconds on large files.
Development builds log an error when that happens. See
[Edit mode: Worker Pool](#edit-mode-performance-and-loading-worker-pool).

Set `preferredHighlighter` when initializing the pool to choose `'shiki-js'`
(the default), `'shiki-wasm'`, or `'highlights'`. The portable worker includes
all backends in its download and initializes the chosen backend. Use the regular
worker entry with your bundler for lazy backend loading. When you choose
`'highlights'`, use [`canUseWASM()`](#utilities-canusewasm) to fall back to
`'shiki-js'` in browsers that can't run it.

#### React

Wrap your component tree with `WorkerPoolContextProvider` from
`@pierre/diffs/react`. All `FileDiff` and `File` components nested within will
automatically use the worker pool for syntax highlighting.

The `WorkerPoolContextProvider` will automatically spin up or shut down the
worker pool based on its react lifecycle. If you have multiple context
providers, they will all share the same pool, and termination won't occur until
all contexts are unmounted.

### Main-Thread Highlighting

Set `mainThreadMaxCharacters` in the pool options to keep small files and diffs
on the main thread. Anything at or below the limit skips the workers: it renders
highlighted immediately when the theme and language are already loaded, and its
first render may be plain text when either still needs to load. Larger content
still goes to the workers. Files count all characters in `contents`; diffs count
the characters on both sides. Main-thread results go into the same
[render cache](#worker-pool-render-cache) as worker results, and
`primeFileHighlightCache()` / `primeDiffHighlightCache()` follow the same rule.

We recommend using this with the `'highlights'` backend, which is fast enough
that a worker round trip usually costs more than the highlighting itself. Start
with `mainThreadMaxCharacters: 100_000`, which should cover most files. If you
tune the limit, aim to keep most or all main-thread highlighting under about 2ms
on the devices you support. When the option is unset, every highlight uses a
worker. If you fall back to `'shiki-js'` with
[`canUseWASM()`](#utilities-canusewasm), leave the option unset for that case so
Shiki stays in the workers.

### Worker Errors

`initialize()` resolves when the first worker acknowledges the current render
options. It can start highlighting queued files and diffs immediately. The other
workers join as they become ready.

If theme or language loading fails before workers start, `initialize()` rejects
with the loading error. Call it again to retry with the same language preloads,
or pass a replacement list to `initialize(languages)`. Overlapping calls wait
for the same attempt.

Each worker attempt gets the full `workerInitializationTimeout` (5 seconds by
default). If the first worker fails or times out during startup, the pool tries
one replacement in the same slot. A slot fails if its replacement also fails or
times out. Healthy workers keep highlighting. If every slot fails, pending cache
primes reject and components highlight on the main thread.

After the pool has started, losing its last ready worker also switches
highlighting to the main thread until another worker joins. `isInitialized()`
still reports that the pool started successfully.

`getStats()` returns the current counts. `subscribeToStatChanges(callback)`
calls the subscriber immediately and batches subsequent updates once per
animation frame.

- `managerState` tracks initialization. It stays `initialized` after the first
  worker joins, even if all available workers later fail.
- `configuredWorkers` is the number of worker slots.
- `readyWorkers` counts workers available for highlighting, including those
  already busy.
- `retryingWorkerSlots` counts slots with a replacement attempt in progress.
- `failedWorkerSlots` counts slots that have used up their attempts or time.
- `workersFailed` means all worker slots ran out of attempts. It stays true
  during recovery until the first replacement is ready.

Call `retryFailedWorkers()` from an explicit trigger, such as a retry button.
Each currently failed slot gets one attempt with a fresh timeout. The promise
resolves with current stats when those attempts settle. A call with no failed
slots resolves immediately. Triggering a retry on every stats update can keep
retrying the same persistent failure.

```ts
retryButton.addEventListener('click', () => {
  void workerPool.retryFailedWorkers();
});
```

By default the pool logs native worker `error` events with `console.error`, and
the browser also reports the worker's uncaught error on the page.

To report worker failures through your own channel instead, pass `onWorkerError`
in the pool options. The pool hands you each native `error` event. Call
`event.preventDefault()` to keep that event from surfacing as an uncaught error
on the page.

<Notice icon={<IconInfoFill />}>
  The hook can run for every failed attempt, including replacements. If your
  application reports once per page, deduplicate those events. A worker script
  that failed to load fires a plain `Event` with no `message` or `error`. A
  worker that threw fires an `ErrorEvent`.
</Notice>

A promise the pool settles without a result rejects with an error exported from
`@pierre/diffs/worker`: `WorkerPoolTerminatedError` (the pool was terminated
while the operation was pending), `WorkerPoolTaskCanceledError` (the task was
superseded or dropped before a worker answered) and `WorkerPoolWorkerError`
(worker setup failed and no usable worker remained). When every slot in a
multi-worker pool fails, `WorkerPoolWorkerError.cause` is an `AggregateError`
with the last error from each slot. `isWorkerPoolCancellation(error)` is true
for the first two error types. `isHandledWorkerPoolError(error)` also detects
worker errors already reported through `onWorkerError`, so a `catch` that logs
highlight failures can skip those errors.

### Render Cache

<Notice variant="warning" icon={<IconCiWarningFill />}>
  This is an experimental feature being validated in production use cases. The
  API is subject to change.
</Notice>

The worker pool can cache rendered AST results to avoid redundant highlighting
work. When a file or diff has a `cacheKey`, subsequent requests with the same
key will return cached results immediately instead of reprocessing through a
worker. This works automatically for both React and Vanilla JS APIs.

<Notice icon={<IconInfoFill />}>
  Caching is enabled per-file/diff by setting a `cacheKey` property. Files and
  diffs without a `cacheKey` will not be cached. The cache also validates
  against render options — if options like theme or line diff type change, the
  cached result is skipped and re-rendered.
</Notice>

Results highlighted on the main thread through
[`mainThreadMaxCharacters`](#worker-pool-main-thread-highlighting) are cached
the same way.

### Editing

Edit mode starts from the pool's rows when it can. A file or diff with a
`cacheKey`, rendered by a pool whose highlighter options set
`useTokenTransformer: true`, waits for a highlight still in flight before its
session starts, instead of highlighting again on the main thread. React and
`CodeView` wait for you; vanilla code awaits `instance.prepareForEditing()`
before `editor.edit()`. See
[Edit mode → Worker Pool](#edit-mode-performance-and-loading-worker-pool).

### Architecture

The worker pool manages a configurable number of worker threads that each
initialize their own selected highlighter instance. Tasks are distributed across
available workers, with queuing when all workers are busy.
